# Design

## Context

In the admin statistics dashboard (`/admin/statistics`), domain breakdown tables read from `MAIL_STATISTICS`, whereas the 24-hour and 7-day activity charts are generated by `EmailStatisticsService`, which currently queries `MailTransactionRepository.findStatsSince()`. Because legacy XCMailr never recorded silent drops (`status 100`) as individual audit log rows in `mailtransactions` and transaction logs are pruned after `max-age-hours` (default 168h), `mailtransactions` contains only ~150–250 sample records per day, while `MAIL_STATISTICS` contains the true aggregate volume (over 600,000 emails over 7 days).

See `proposal.md` for motivation and scope.

## Goals / Non-Goals

**Goals:**
- Unify chart data generation on `MAIL_STATISTICS` so that 24-hour and 7-day activity charts strictly match the totals and breakdowns shown in the sender domain tables.
- Keep chart generation fast and lightweight using JPQL `SUM()` aggregates rather than scanning raw transaction logs.
- Support both 7-day calendar day grouping and 24-hour sliding hourly grouping with continuous zero-filling.
- Preserve 100% backward compatibility with `ChartDataDto` and existing Chart.js frontend templates.

**Non-Goals:**
- Modifying the Flyway database schema (existing `MAIL_STATISTICS` table schema with `V5` already supports `DROP_COUNT`, `FORWARD_COUNT`, `STORE_COUNT`).
- Changing the transaction audit log view (`/admin/transactions`), which legitimately inspects individual raw audit entries.
- Altering the retention cleanup mechanisms in `ExpirationScheduledService`.

## Decisions

### Decision 1: Query Aggregated Projections from `MailStatisticsRepository`
Instead of querying `MailTransactionRepository`, introduce dedicated aggregation query methods on `MailStatisticsRepository`:
1. `findDailyTrafficStatsSince(Date startDate)`: Aggregates `SUM(forwardCount)`, `SUM(storeCount)`, `SUM(dropCount)` grouped by `ms.key.date` since `startDate`.
2. `findQuarterHourTrafficStatsSince(Date startDate)`: Aggregates `SUM(forwardCount)`, `SUM(storeCount)`, `SUM(dropCount)` grouped by `ms.key.date` and `ms.key.quarterHour` since `startDate`.

*Alternative considered:* Loading all `MailStatistics` entity rows into Hibernate memory and summing in Java.
*Why rejected:* Unnecessary entity instantiation and memory overhead; database SQL grouping is orders of magnitude faster and returns at most 7 rows for weekly stats and 192 rows for 24h stats.

### Decision 2: Quarter-Hour to Hourly Bucket Mapping in Java
For the 24-hour sliding window, the query retrieves entries where `ms.key.date >= yesterdayDate` grouped by `date` and `quarterHour`. In Java:
```java
ZonedDateTime entryZdt = entry.getDate().toLocalDate().atStartOfDay(zoneId).plusMinutes(entry.getQuarterHour() * 15L);
```
If `entryZdt` falls between `startZdt` (inclusive) and `endZdt` (exclusive), calculate:
```java
int bucketIndex = (int) ChronoUnit.HOURS.between(startZdt, entryZdt);
```
Each hourly bucket sums the 4 quarter-hour intervals (`4 * hour + [0..3]`).

*Alternative considered:* SQL-level grouping using `quarterHour / 4` or date-truncation functions.
*Why rejected:* SQL integer division and date-time functions differ across database dialects (H2 vs PostgreSQL vs MySQL). Doing the 192-slot aggregation in memory is dialect-agnostic, hermetic, and takes less than a millisecond.

### Decision 3: Service Dependency Injection
Update `EmailStatisticsService` constructor to inject `MailStatisticsRepository` instead of `MailTransactionRepository`. Remove `MailTransactionRepository` dependency from `EmailStatisticsService`.

*Alternative considered:* Keeping `MailTransactionRepository` as an optional fallback.
*Why rejected:* Redundant and misleading; charts should always represent total email traffic from `MAIL_STATISTICS`.

## Risks / Trade-offs

- **[Risk]** In-flight emails in `MailTransactionQueueService` buffer have not yet been flushed to `MAIL_STATISTICS`.
  → **Mitigation:** The buffer flushes every 60 seconds (`interval-minutes: 1`). Both tables and charts read from `MAIL_STATISTICS` simultaneously, ensuring they remain completely synchronized with at most 1 minute of latency.
- **[Risk]** Time zone boundary shifts between SQL `Date` and `ZoneId`.
  → **Mitigation:** `MailStatisticsKey` dates are stored normalized to local midnight by `ExpirationScheduledService`. Using `date.toLocalDate().atStartOfDay(zoneId)` guarantees exact alignment with the system's active time zone.
